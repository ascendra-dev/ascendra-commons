Domain Events — Admin Console

Screen mocks for the domain-events module's admin surface, each mapped to the endpoint that backs it. Every read is gated @RequiresAction('domain-events.view'); there is no tenant scoping — domain-events has no tenantId.

Scope — delivery only, never a listener outcome. Every screen here answers "did the event fire, and was anyone listening" — never "what happened after." Whether a listener's own handling then succeeded (the audit record actually wrote, the notification actually sent) is that listener's own module's concern, surfaced in audit-logging's and notification's own admin screens, not here.

Reading "dispatch_failed." This means the transport itself broke before reaching any listener — genuinely rare. A listener rejecting (e.g. an @OnCriticalEvent() audit listener throwing) is not shown as a failure here — that row still reads delivered, because the hand-off did happen. The listener's own outcome is tracked in that listener's own module.

Listener Catalogue

GET/domain-events/listener-catalog Live

"What the code says should be listening" — every @OnEvent()/@OnCriticalEvent() binding discovered live in the running app, independent of whether the event has ever actually fired. No database behind this read.

Gate: domain-events.view. In-process transport only — a broker's listeners live in other services and aren't discoverable this way.

Wiring Health

client-side join of Event Catalog + Listener Catalogue Live

Cross-references what the code says should listen against what has actually fired, catching two different bugs neither endpoint surfaces alone.

Gate: domain-events.view (both underlying reads). No new API — a browser-side join of two already-Live endpoints.

Overview

GET/domain-events/stats Proposed

The landing dashboard — delivery volume and shape at a glance, so an operator notices "an event stopped firing" or "no-listener rate spiked" without running a query.

Gate: domain-events.view.

Missing API. No aggregation endpoint exists — deliveryCatalog() returns per-event totals, not a time series. Proposed: GET /domain-events/stats?window=7d → { perDay[], topEvents[], noListenerRate, dispatchFailedRate }, computed with GROUP BY date_trunc('day', delivered_at) over commons_domain_events_delivery.
