Domain Events — Admin Console

Screen mocks for the domain-events module's admin surface. Every read is gated @RequiresAction('domain-events.view') — a platform persona, not tenant-scoped: a delivery row has no tenant (the payload isn't stored), and the wiring it shows is the whole app's.

Why this console exists. A domain event is invisible both when it works and when it's miswired. This is where you see what fired and who was listening — and the three wiring bugs nothing else catches: an event firing into nothing, a critical listener raised with emit() (its failure silently swallowed), and a listener whose event never fires.
What a row is. One emit() / emitCritical() call — delivery only: was anyone subscribed, did the hand-off happen. Never what a listener then did (that's audit's or notification's own log), and never the payload. Rows are buffered and written every 10 seconds. Every period is on when the event occurred; the app keeps deliveries 90 days (its prune).

  • Critical listener, raised with emit() (red) — the event has an @OnCriticalEvent() listener but some producer raised it with emit() in the period: that listener's failure is swallowed. Fix the producer (use emitCritical()).
  • Fires into nothing (amber) — fired, and no listener is wired in the code (its deliveries are no_listeners). A typo in a listener's event name, or a subscriber never built.
  • Never fires (blue) — a listener is wired, but nothing raised the event in the period. Dead code, or a producer-side typo. Judged on everything retained by default — a shorter period can be a quiet week.
  • Problems sort first. An event name with deliveries opens Deliveries filtered to it. The listener catalogue only sees this process: listeners in another service (a future broker transport) don't appear.
