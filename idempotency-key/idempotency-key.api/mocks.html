Idempotency Keys — Admin Console

Screen mocks for the idempotency-key module's admin surface. Every read is gated @RequiresAction('idempotency.view') — an ops/support persona, not tenant-scoped (a claim's scope is opaque to the module). A claim's saved response body is a separate grant, idempotency.view-response: it can hold personal data.

Why this console exists. Idempotency is invisible both when it works and when it quietly fails. This is where you see the duplicates it absorbed (a retry answered with the saved response, a double-click turned away with a 409), and the one failure nothing else shows: a request taken over as stale while it was still running — work that ran twice.
What a row is. One claim per Idempotency-Key and scope — the first request with that key. Its replays and 409s are counted in memory and added to the row every 10 seconds, so counts can trail by up to ~10s. Claims are kept 24 hours (the app's cleanup), so every period here is at most the past 24 hours.

  • Each list is a table card with its title in an lg header, scrolling after 5 rows (visibleRows).
  • Duplicates absorbed is the pattern working: every one is a request that did not run again. A route's number opens Claims filtered to that route and period.
  • Reclaimed is a warning, Ran twice an alarm (red only when > 0). Either opens Claims for the period; if Ran twice moves with real traffic, staleAfterSeconds is too low for that endpoint.
  • In progress shows each claim's age. One much older than the app's staleAfterSeconds (amber) is a crashed or hung handler — retries get 409 until it goes stale. A row opens the Claim sheet.
  • Times are the viewer's local time (formatDateTime).

  • Status carries the saved response's status code. A 4xx (amber) means every retry within 24h gets that same error back — the case behind "my retry keeps failing".
  • Replayed / 409s — repeat requests answered with the saved response / turned away while the first was running. Muted at 0.
