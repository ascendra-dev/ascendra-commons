Notification — Console

Screen mocks for the notification module's console — what went out, what didn't and why, and the configuration that decides it. One console for two audiences: a platform admin sees every tenant and the platform's own defaults and accounts; a tenant admin sees its own tenant and the defaults it inherits — the API forces it, the screens just don't offer the rest. Every signed-in user gets an Inbox and My notifications. Numbers are the sandbox's seeded data.

Why this console exists. A notification fails quietly — nobody tells you the reminder never left. A template with a typo shows a customer {{invoiceNo}}; a revoked provider key fails every SMS for ten days; a dead mailbox keeps bouncing and wears down the sender's reputation. This is where you see that, fix the configuration, and check the fix with a test send.
The model. The app declares its notification types in code (name, audience, variables with samples; some required — always sent). Each type is routed to channels — email, SMS, WhatsApp, in-app — by a default route a tenant may override; each channel needs a template (default, or a tenant's white-label) and, except in-app, a provider account: the tenant's own, or the platform's when the app allows the fallback. Every send attempt is a delivery row per channel: sent → delivered / bounced (the provider's callback), failed, or skipped (suppressed after a hard bounce, or the user opted out).

Suppressions

GET/notifications/suppressionsDELETE/suppressions/:idLive

Recipients a channel stopped sending to — a hard bounce or a spam complaint reported by the provider. Every send to them is skipped until someone removes the entry (the mailbox was fixed, the number re-verified).

Gate notification.view; removing takes notification.manage_config — audited. An entry applies to the whole app (a dead address is dead for every tenant).
