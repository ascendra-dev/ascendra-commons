File storage — Console

Screen mocks for the file-storage module's console — every file the app holds, what it is, whose, how long it's kept, who opened it, and the rules uploads must pass. One console for two audiences: a platform admin sees every tenant, sets storage limits and runs cleanup across buckets; a tenant admin sees its own tenant's files and tightens its own upload rules — the API forces it, the screens just don't offer the rest. Numbers are the sandbox's seeded data (30 days, Asia/Karachi).

Why this console exists. Files pile up quietly and carry the most sensitive things the app holds — passports, bank statements, contracts. Someone needs to see what is kept and for how long, who opened a document, why uploads are being refused, which tenant is filling its space, and what can be cleaned up — and to put a file beyond deletion when a dispute or investigation needs it kept.
The model. The app declares its upload types (categories) in code — what a KYC document or an invoice attachment may be: content types, extensions, a size band, the bucket, what to do with a file the scanner can't read, and how long it is kept. A tenant may only tighten them. Every upload passes the app-wide rules, the type's rules, a check that its bytes are what it claims, the tenant's storage limit and a malware scan; a refusal is logged. A stored file is attached to one or more business entities (an invoice, a dispute…); detached from all of them it is an orphan. Its retention date is fixed at upload: before it, a tenant can't delete it; after it, the nightly retention run deletes it — unless it is under legal hold.

States

  • Platform support — no Open, no Hold, no Delete: "Opening a file takes file.view_content".
  • Shared link rows in the access log — "via a shared link" (no person).
  • Several attachments — each with Detach; detaching the last makes it an orphan (the file stays).
  • Not scanned — "The scanner couldn't read this file (password-protected?). Dispute evidence allows that." beside the scan row.
  • Deleted file — its id now 404s: "This file was deleted" (the audit log says by whom and why).
