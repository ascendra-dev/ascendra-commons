Background Jobs — Admin Console

Screen mocks for the background-jobs module's admin surface, each mapped to its endpoint. No tenant scoping — jobs have no tenantId. Reads gated @RequiresAction('job.view'); the manual trigger gated 'job.run'. Screens marked Proposed are legitimate parts of a jobs console the API doesn't serve yet.

By design. "Missed schedule" is never a stored row — it's derived in the dashboard from a per-job cadence hint. Scheduling itself lives in the vertical (a @Cron wrapper), so "Pause / Disable" below is proposed with a caveat, not assumed.

Failed Items

GET/jobs/:name/failed-itemsProposed

Which items a job keeps failing on, across runs — the "chronic offender" view for triage.

Missing API. failedItemRefs is stored per run, so "which items failed the last N runs" means paging every run and diffing client-side. Proposed: GET /jobs/:name/failed-items?minRuns=3 → items with their failure streak. Not a dead-letter queue — per-item retry is Model 2.

Lock Inspector

GET/jobs/locksProposed

Which advisory locks are currently held and since when — so a lock stuck by a crashed instance is visible before it silently blocks a job for hours.

Gate: job.view. Read-only — a force-release action would be a separate, dangerous, audited endpoint (not proposed here).

Missing API. GET /jobs/locks → held commons_jobs_lock rows: { lockKey, holder, acquiredAt, lockedUntil }. A row whose lockedUntil is in the past but still present is the smoking gun.

Alerts & Overdue

GET/jobs/alertsProposed

The subset of the dashboard that needs attention — overdue jobs, failure streaks — as a feed an operator can work through and acknowledge.

Missing API. overdue / consecutiveFailures are computed in listJobStatus but nothing pushes them and there's no acknowledge state. Proposed: GET /jobs/alerts + POST /jobs/alerts/:id/ack, and an outbound webhook config so a failure pages someone without a human watching the screen.

Pause / Disable

POST/jobs/:name/pauseProposed

Stop a misbehaving job from running without a deploy — e.g. a payout sweep hitting a broken provider and failing every 6 hours at 3am.

Missing API — with a caveat. Scheduling lives in the vertical (a @Cron wrapper calling IdempotentJobRunner.run), so a true pause needs a shared "is this job paused" flag the wrapper checks. Proposed: a commons_jobs_pause row + POST /jobs/:name/pause / DELETE /jobs/:name/pause (audited, job.run-gated), and listJobStatus gains a paused field. If the team decides scheduling stays entirely the vertical's, this is documented as out of scope instead.
