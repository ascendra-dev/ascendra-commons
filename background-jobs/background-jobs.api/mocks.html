Background Jobs — Admin Console

Screen mocks for the background-jobs module's admin surface. Reads are gated @RequiresAction('job.view'), Run now 'job.run' — a platform persona, not tenant-scoped: jobs have no tenant (one run covers every tenant's due items).

Why this console exists. A scheduled job fails quietly — nobody is waiting on it. This is where you see the four ways it goes wrong: a job that fails outright every run, one that keeps failing on the same item, one that stopped running (overdue — a missed schedule leaves no row, so it's derived from a cadence), and a lock left by a dead process blocking it.
What a row is. One run that took the job's lock — findDueItems(), then each item, failures isolated per item. Three kinds: clean, with failed items (they stay due and retry next run), and job failed (findDueItems() threw — nothing processed). A run that found the lock taken isn't a run and isn't recorded. Every period is on when the run started; the app keeps runs 90 days (its own job-run-pruner job).

Locks

GET/jobs/locks Live

Which job locks are taken right now — a run in progress, or one a crashed process left behind. Opened from the Overview's header.

Gate: job.view. Read-only — no force-release.

JobHolderTakenLease untilState
statement-exportsandbox-api-7f2a#4242#d1ed0b4c20 Oct 06:0020 Oct 06:15expired — holder died
search-reindexZakas-MacBook-Air.local#43820#ac584b1522 Oct 19:5622 Oct 20:11held — running
  • A released lock's row is deleted, so every row is either a run in progress (held, blue — its holder keeps extending the lease) or a holder that died mid-run (expired, red). An expired lock blocks nothing new — the next run takes it over — but it marks a run that never finished and was never recorded.
  • The holder is host#pid#nonce — which process. A job name opens its Job screen.
  • On the session-level advisory lock (supported: false): "This app's lock can't be listed — it uses Postgres advisory locks, which leave nothing to read. Switch to the lease lock to see locks here."
