Authorization — Admin Console

Screen mocks for the authorization module's admin surface, each mapped to its endpoint. Reads gated @RequiresAction('authz.view'); role assignment 'authz.assign_roles'; delegation 'authz.manage_delegations'; catalog editing 'authz.manage_catalog'. A non-platform actor may only assign roles in their own tenant and cannot assign a grantsAll role. Screens marked Proposed are legitimate but unserved.

By design. Editing which actions a role grants is deliberately not an endpoint — that's migration / seed territory, REVOKEd from the app's DB role. This console assigns existing roles, manages delegations, and describes actions; it never rewrites the permission matrix.

Who Can Do X

GET/authz/who-canLive

The reverse of the explainer — given an action, every role that grants it and every user who holds such a role or an active delegation. The first question in an incident: "who could have done this?"

Gate: authz.view (the same read gate as the rest of this controller — no new gating infrastructure was added); a cross-tenant call just omits tenantId. Query: ?action=payout.approve&tenantId=t_kairos → { action, tenantId, roles: [{ roleId, grantsAll, holderUserIds[] }], delegations: [{ id, granterId, granteeId, expiresAt }] }, built from role_permission + grantsAll roles + active delegations (Postgres actions @> ARRAY[...] containment).
