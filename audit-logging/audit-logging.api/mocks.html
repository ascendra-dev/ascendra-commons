Audit Logging — Admin Console

Screen mocks for the audit-logging module's admin surface, each mapped to the endpoint that backs it. Only Retention & Volume remains Proposed — a legitimate part of an audit console that audit-logging.api doesn't serve yet (deliberately deferred; see its section below). Every read is gated @RequiresAction('audit.view'); a non-platform actor's query is auto-scoped to their own tenant.

Scope. audit-logging is write-once — there is deliberately no update or delete endpoint, and none is proposed. "Operations" screens below are read-only views over volume and retention, not controls.

Coverage & Gaps

POST/audit/coverage Live

Drift detection — which entity types and audited actions the vertical declared but that have never actually produced an audit record. A silent gap in the audit trail is a compliance risk.

Gate: audit.view. Tenant-scoped for non-platform actors, same convention as the list; platform-admin in practice (needs the full picture across tenants).

Per-request comparison. Mirrors authorization's actionCatalogHealth(knownActions) — no catalog table. POST /audit/coverage with the vertical's declared { entityTypes[], actions[] } → { kind, value, count, assessment }[], one row per declared entry, counted live against commons_audit_event.

Export

GET/audit/events.csv Live

Hand an external auditor a filtered slice of the log as one file.

Gate: audit.view (same as the read). Non-platform actor → tenant-scoped, exactly like the list.

Bounded ranges only. GET /audit/events.csv?…filters reuses the same AuditQuery filters and returns one text/csv response for a normal page (same default/max limit as the JSON list). For a quarter/year of a busy tenant, an async export job that writes a file to file-storage and notifies on completion (the same pattern the notification module documents for a long-retention archive) is a deliberately separate, not-yet-built piece of work — the row below illustrates that shape, not something this endpoint does.

Retention & Volume

GET/audit/retention Proposed

Read-only health of the audit store itself — how far back it goes, how big it is, and whether anything is pruning it.

Gate: audit.view, platform-admin only.

Missing API. GET /audit/retention → { oldestRecordAt, rowCount, approxBytes, retentionJob: null | { keepForDays, lastRunAt } }. No delete endpoint is proposed — audit records are write-once; a retention job, if a deployment needs one, is a consuming-project cron, not part of this API.
